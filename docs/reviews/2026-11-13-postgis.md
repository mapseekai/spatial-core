## 审查方式与负载假设

按用户要求派发两个独立子 agent：

- `review_transactions`：连接、TLS 配置与取消、事务原子性、触发器、并发和元数据一致性。
- `review_data_contracts`：vector/raster 输入、字段精度、ZIP 路径、WKB、分块与异构元数据。

主 agent 交叉检查源码和复现日志，另外执行 26 组桌面真实数据导入。按 rust-skills 检查所有权、阻塞线程和错误传播，按 ponytail-review 检查完整调用链、可复现正确性与最小修复方向。当前 checkout 没有 CodeGraph/GitNexus 索引，依据实际源码分析。

审查假设包括：库由外部 Tokio runtime 和 deadpool 连接池驱动；运行时可能限制 blocking 线程；ReplaceRows 面向保留既有 trigger/约束的普通表；metadata 读取可能与外部 DDL 并发；取消通道可能单独失败。上述均对应现有接口或设计承诺，不引入 Append、业务编排或新输入格式需求。

证据、独立消费者源码、原始日志、裁块来源与源码哈希保存在 [审查附件](../../artifacts/reviews/2026-11-13-postgis/README.md)。没有保存 DSN、密码或用户原始数据副本。

## 确认的问题

### R1 · P1：正常栅格被 catalog 精度检查误拒绝

位置：[raster/table.rs:92](../../src/postgis/raster/table.rs#L92)。最终校验将 `raster_columns.scale_x`、`scale_y`、`nodata_values` 与源完整 f64 严格比较，而测试版本的 PostGIS catalog 对这些值保留 10 位小数。

实测同一个 raster 中 `ST_ScaleX=2.35176759123e-05`，catalog 为 `2.35177e-05`；`ST_BandNoDataValue=0.1234567890123`，catalog 为 `0.123456789`。像元和栅格本身正确，校验却返回 `SchemaMismatch("database finalization check failed")` 并回滚。`scale=0.1` 的对照通过。

受影响的真实输入包括 Cloud.tiff 裁块、J50D001006.tif 裁块，以及 Landsat 裁块重投影到 EPSG:3857；另一个 agent 独立验证了高精度 NoData 和普通 4326→3857 warp。因此这不是罕见文件格式问题，也不是源数据损坏。

修复方向：catalog 比较遵循其实际精度语义，另外从实际 raster 值检查需要保真的网格/NoData。**不能通过舍入源仿射变换或 NoData 来迎合 catalog。** 回归应断言导入成功，并从 `ST_ScaleX`、`ST_BandNoDataValue` 读回完整源值。

### R2 · P1：CRS 校验与生产者竞争 blocking pool，形成死锁

位置：[connection.rs:185](../../src/postgis/connection.rs#L185)，关联 [transaction.rs:263](../../src/postgis/transaction.rs#L263)、[stream.rs:79](../../src/postgis/stream.rs#L79)。生产者先占用 blocking 线程，发送 metadata 后持续生产；32 项通道填满时等待消费者。消费者进入 COPY 前，又等待 `check_srid` 排入同一 blocking pool 的另一任务。

实测 100 个点、`max_blocking_threads=1`：超过 3 秒仍无进展，显式取消才退出。相同输入与数据库，仅改为 2 个 blocking 线程，即在约 207ms 完成并确认 100 行。更大线程池被多个生产者占满时也有同样的等待环，但本轮没有将该并发扩展情形算作已经执行的压力测试。

修复方向：在有界生产开始前完成必要预检，或通过握手将 CRS 比较放到已有 source worker。避免消费者等待第二个 blocking task、而第一个 task 正等待消费者的结构。单纯提高线程上限不能消除死锁。回归至少在 blocking 线程数为 1 时完成超过通道容量的输入。

### R3 · P2：AFTER/延迟触发器导致成功报告与最终数据不符

位置：[transaction.rs:291](../../src/postgis/transaction.rs#L291)，关联第 335、354 行。`ReplaceRows` 保留触发器，只比较 produced/sent/COPY command tag；后者并不等于所有触发器执行后的最终表计数。

实测目标原有 3 行，AFTER INSERT trigger 删除新行：API 成功报告 `feature_count=3`，数据库最终 0 行。将相同逻辑设为 `DEFERRABLE INITIALLY DEFERRED` constraint trigger 后，API 还会返回提交前的非空 extent，但最终仍是 0 行、空 extent。现有设计明确要求 trigger 的执行结果满足导入契约，不能把该结果当作完整导入成功。

修复方向：明确可支持的触发器契约；在最终检查前执行 `SET CONSTRAINTS ALL IMMEDIATE`，随后验证实际数量并计算 extent，不符则回滚；也可明确拒绝无法保证契约的触发器。最终数量校验只是必要条件，并不能发现保留数量但改写属性/几何的触发器，契约必须明确。回归同时覆盖普通 AFTER 和延迟 trigger，并验证失败后旧数据保留。

### R4 · P2：metadata 可混合旧表结构与新表数据

位置：[vector/metadata.rs:65](../../src/postgis/vector/metadata.rs#L65)，主要为第 68–74 行。REPEATABLE READ 中先读系统目录，到 `SELECT count(*)` 才取得目标表读锁；中间发生 DROP/CREATE 后，按名称执行的数据查询与前面的列定义可能属于不同 relation。

通过本地协议代理在 COUNT 前暂停读取，另一连接把 `old_col integer + Point/4326` 替换为 `new_col text + Point/3857`，两版各写 1 行。API 返回旧列、SRID 4326、0 行、空 extent；当前数据库则是新列、SRID 3857、1 行。该报告不代表任一个完整版本。

修复方向：BEGIN 后，在建立 catalog/data snapshot 前先锁定目标表 `ACCESS SHARE`，随后读取各部分；或可靠检测 relation OID 变化并明确失败/重试。只加 advisory lock 无法排除外部 DDL。回归应允许“完整旧版本”“完整新版本”或明确失败，拒绝混合报告。

### R5 · P2：取消通道失败后仍等待繁忙连接上的 ROLLBACK

位置：[transaction.rs:370](../../src/postgis/transaction.rs#L370)，关联 [connection.rs:56](../../src/postgis/connection.rs#L56)。取消需要单独建立连接；该连接失败后，代码虽保留 `Cancelled + Cleanup`，但仍等待原连接执行 ROLLBACK，后者排在尚未结束的 SQL 后。

实测使用与池匹配的 NoTls，通过本地 TCP 代理保留已有数据连接、关闭新的连接入口。COPY 的 trigger 对 3 行各 `pg_sleep(2)`。取消连接立即得到 ConnectionRefused，但 writer 一秒后仍未返回，约 6037ms 后才回滚并返回取消错误。旧 3 行最终保留。这里不是 TLS 配置错误；若原查询没有结束条件，当前 cleanup 路径没有自身等待期限。

修复方向：取消无法投递时丢弃未确认的连接并保留 cleanup 原因，或给回滚清理设置明确期限后关闭连接；同时明确关闭连接不等于确认服务端立即停止执行。回归应让取消通道单独失败，确认调用不会无限等待，也不会把该连接返还连接池。

### R6 · P2：合法的 ZIP 内部文件路径无法导入

位置：[vector/source.rs:356](../../src/postgis/vector/source.rs#L356)。所有 `/vsizip/` URI 都被递归枚举为目录，明确成员路径也走该分支。

真实 `/vsizip/.../City.zip/City/CN_city.shp` 可由 GDAL 直接打开，但 writer 报 `VSIReadDirRecursive` 返回 NULL。同一归档的根路径可成功导入 385 行。独立合成 Shapefile 和 GeoJSON ZIP 成员也复现同一错误。

修复方向：先尝试按输入 URI 打开数据集，仅在需要定位归档目录内 Shapefile 时使用递归 fallback，保留明确图层选择。回归覆盖 archive 根、子目录、明确 Shapefile 成员和 GeoJSON 成员。

### R7 · P2：文本转 double 绕过精度守卫

位置：[vector/copy.rs:123](../../src/postgis/vector/copy.rs#L123)。StringValue 映射 DoublePrecision 只检查 `parse::<f64>()` 是否成功，解析本身已经可能舍入；同文件对原生 Integer64→double 却有无损检查。

实测文本 `"9007199254740993"` 成功提交后读回 `9007199254740992`；`"1.0000000000000001"` 读回 `1`。至少前一个整数案例与已有原生整数策略直接矛盾，也不符合文档承诺的无损字段恢复。

修复方向：统一文本与原生数值的转换契约，用未先经过 f64 的源值进行精度校验；至少拒绝不能精确表示的整数字符串。若决定允许一般文本→浮点近似转换，必须显式修订契约并与调用者可见行为一致；精确 decimal 继续使用 NUMERIC。回归需覆盖 2^53 两侧和高精度小数，禁止以“能解析”为无损证据。

### R8 · P2：不同 SRID 的 raster extent 被直接混合

位置：[raster/metadata.rs:65](../../src/postgis/raster/metadata.rs#L65)。检测到多个 SRID 后仍直接对所有 hull 做 `ST_Extent`。

实测 EPSG:4326 的 `[100,30]` 附近与 EPSG:3857 的 `[11131949,3503549]` 附近共同返回 `extent=[100,29.98,11131969,3503549]`。该值混合度和米，无法作为已定义 CRS 下的范围。`heterogeneous=true` 无法解释 extent 的可用条件，因为普通边缘 tile 尺寸不同也会置该标记。

修复方向：多个 SRID 时返回 `None`、明确错误或分 SRID 范围；如要合并，必须由明确的目标 CRS 定义转换。回归同时覆盖单一 SRID 的边缘 tile 和混合 SRID 表，前者仍应给出有效范围。

## 未升格为缺陷的观察与验收边界

- OutDB 的 server_path 不存在时，登记可成功，随后 ST_Value 失败。当前设计将路径可见性与访问权限交由部署保证，因此本项记录为已验证限制。有效只读挂载路径已实际读取像元；“登记成功”不能代替部署端可读性检查。
- 不带 CRS 的 Parquet、未知几何族输入按当前默认契约拒绝；没有把拒绝算作成功。另有 GDAL 无法打开的损坏 TIFF 和缺少仿射/CRS 的 RPC 类影像，未纳入 26 组导入用例。
- 本轮没有修改库实现或自动加入回归。建议先修复 R1、R2，再处理 R3–R8；每项以文中复现与对照转换为回归测试。取消、触发器和文本浮点的可保证契约应同步写回设计与 Rustdoc。
- 未执行生产持续负载、峰值 RSS、真实 S3、跨机器 OutDB、Linux 客户端或 Windows、远端 CI；数据库在 Linux Docker 中运行不代表 Rust 客户端经过 Linux 验证。TLS 故障测试本轮只覆盖匹配的本地 NoTls 取消连接失败。
- 没有修改相邻消费者、提交、推送或发布；未在外部 tracker 创建事项，8 项问题及复现已保存在本地报告。
